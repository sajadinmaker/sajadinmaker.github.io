Preventing double delivery under concurrent workers

Two workers can observe the same pending delivery. The claim has to be atomic.

HookFlow started with one worker, and life was simple: grab due rows, POST them, mark them done. One worker can't race itself. Then I added a second worker, and "grab due rows" quietly became a lie — both workers could read the same free row in the gap before either wrote. Nothing fails loudly. You just send someone's webhook twice, and find out from them. That's the kind of bug that makes you add a second worker very carefully.

The fix wasn't a lock held across the HTTP call (imagine holding a database lock while waiting on a customer's slow server — no). It was a claim: mark the rows yours in one indivisible step, then go do the slow work knowing nobody else will touch them.

The mechanism

claim_due_deliveries takes ownership with a single UPDATE whose subquery skips anything already claimed under a live lease. The database lines the two racers up, and the loser simply finds fewer rows left — its subquery runs against the winner's already-committed changes. A SELECT followed by an UPDATE could never promise that. On PostgreSQL the subquery also takes FOR UPDATE SKIP LOCKED, so workers never queue up behind each other (SQLite has no row locks, but it lines writers up on its own). Every claim carries a token and a 60-second lease:

  • A worker only settles rows it still holds the token for — and a successful settle hands the claim straight back.
  • If a worker dies mid-delivery, its rows unlock themselves when the lease runs out. Stuck rows are impossible by construction, and a sweeper tidies up the stale claims.
  • Rate-limited deliveries go back without a claim, so they wait their turn instead of getting stranded.

The test that matters

test_concurrent_claimers_receive_disjoint_rows — the name is the whole story. It points real, overlapping workers at the same rows and demands disjoint sets back: zero double delivery. Around it, smaller tests pin down the rest: expired leases become claimable again, the sweeper only frees stale rows, settling releases the claim, and single-worker mode skips claiming entirely (it would be pure overhead when nobody can race you).

What I kept honest

Two things I won't claim. First: the replica story is split — the delivery claim is safe across replicas, but the rate limiter falls back to per-process memory without Redis, and that's single-replica only. It's in the README limitations, not the fine print. Second: these claim tests run on SQLite; the SKIP LOCKED branch only fires on PostgreSQL. So I talk about the mechanism and the tests — not a Postgres concurrency benchmark I haven't run. Someday, with a real load rig. Not today.
