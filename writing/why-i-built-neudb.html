Why I built neuDB

A small database project about transparency, persistence, and AI memory.

Most AI apps stash memory behind a managed database or some hosted vector service. Convenient — until something goes wrong at 1am and you're staring at a black box, wondering what the agent actually remembered. I got tired of that feeling, so I built neuDB: a tiny database where I could see every single piece. How records get saved, how writes survive a crash, how semantic search fits into a normal data model. No magic, just files I can open.

Each table is one human-readable JSON file. Every record gets a UUID, and the engine does the basics: insert, filter, update, delete, text search. Writes go through a temp file, fsync, then an atomic swap — so a crash leaves you with the old file or the new file, never half a file. Threads in the same process take turns via per-file locks. It's deliberately modest. But you can cat any of it, and that was the whole point.

The bug my tests caught

This is my favourite part. When I added concurrency tests, my first design cleaned up stray temp files every time a table opened — sounded tidy. The new test broke it immediately: the cleanup deleted another writer's temp file mid-write, and its atomic rename blew up with a FileNotFoundError. My tidy design was the bug. Cleanup-on-open is just wrong when two writers exist. Now sweeping is explicit maintenance with an age threshold, and the whole incident lives in docs/recovery.md. Honestly? Watching my own test catch my own race felt better than shipping the feature. That loop — write the test, watch it catch something real, fix the design — taught me more than the database did.

What I measured

Numbers from benchmarks/bench.py, because feelings aren't benchmarks: 138 inserts a second (p95 13.7ms) at 2,000 rows, sliding to 56/s (p95 34.4ms) at 5,000 rows. Every write rewrites the whole file, so O(N) cost confirmed by measurement, not theory. Four threaded writers doing 100 rows each lost nothing: 400/400. That table is the real deliverable, I think — it tells you exactly where this design stops working (don't go past ~10K rows a table), which makes the *next* design concrete instead of hand-wavy.

The AI layer adds optional embeddings to message records. Semantic search runs on cosine similarity, and plain text search still works when no embedding model is installed. On top of that, an agent pulls up relevant old messages before calling an LLM and stores the new exchange after. It's a small long-term memory loop — runs locally with Ollama or talks to any OpenAI-compatible provider.

And the limits are the point, not the fine print. JSON files and linear scans are right for a local tool and wrong for a busy service. A production version would need indexes, transactions, coordination across processes, pagination, and a proper vector index. Writing those down is what makes the project useful: a simple thing that shows you exactly which hard problem to solve next.

neuDB is available on GitHub and is published on PyPI, with the full case study at projects/neudb.
