HookFlow: accept first, deliver later

Webhook delivery is a persistence problem, not a POST problem.

The naive way to send a webhook is one line: requests.post(customer_url, json=event), right there in the request handler. I did that first, like everyone does. Then I thought about what happens when the customer's server is deploying at that exact second — my API just hangs, waiting on their worst day. Their timeout becomes my latency, and if the POST fails, the event is gone. That one line was doing way too much trusting.

So I flipped the order. HookFlow saves the event and its delivery row first, tells the producer "got it," and lets a worker deal with the unreliable part in the background. The POST still happens — it's just no longer anyone's problem except the worker's.

Constraints

I gave myself a small box on purpose: one service, one database, one queue. No Kafka, no Kubernetes. Redis had to be optional, because a side project that needs four daemons running to be correct is never actually correct on my laptop at midnight. And receivers had to be able to verify every delivery and survive getting one twice.

Architecture

Client → FastAPI → PostgreSQL → Redis (hint) → Worker → webhook

Ingest validates the URL and payload (under 256KB), checks idempotency, then commits Event + Delivery(status=queued) in a single transaction before Redis ever hears about it. Redis only carries a wake-up hint — the worker polls due rows regardless, so if Redis drops the hint, delivery is late, not lost. I measured it on SQLite via TestClient: 39 requests a second at p95 29ms for 1KB payloads. Barely changes with payload size, which told me the cost is the transaction, not the bytes. Good to know, slightly annoying to learn.

The decision that mattered

At-least-once delivery plus idempotency keys, instead of pretending I could build exactly-once. There's a UNIQUE(endpoint_id, idempotency_key) constraint in the database, and the code catches the IntegrityError — because here's the thing I keep relearning: the app-level "does this key exist?" check works fine until two requests arrive at the same time, and then it lies to you. The constraint is the real guarantee; the application check is just the polite path. Same thinking behind indexing the worker poll on (status, next_attempt_at): correctness shouldn't depend on tables staying small.

Failure and backoff

Retries with a dead end: 1m → 5m → 30m → 2h → 12h, five attempts, then the delivery goes to a dead-letter state with a replay endpoint to bring it back. Successes can't be replayed on purpose — replaying one would poke the receiver's side effects twice, so the API answers 409. Every delivery is HMAC-signed per endpoint, so the receiver can verify it independently of whatever the network did to it.

What I'd change

Update 27 Sep 2026: the three gaps named below are since closed — per-tenant API keys, Alembic migrations, and a Next.js operator dashboard all exist now. The case study is current; what follows is the original note.

The gap that bothered me most was scope: no multi-tenant auth. Endpoint secrets authenticated receivers, not producers — anyone with network access could register endpoints. I wrote that down instead of hiding it, and per-tenant API keys were the next change. After that: Alembic (it was create_all at the time), real Postgres load numbers, and a dashboard on /metrics. A side project earns trust by stating its threat model plainly, I think — including the parts that are embarrassing.
