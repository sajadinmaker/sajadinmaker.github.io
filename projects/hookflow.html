HookFlow

Reliable webhook and event delivery infrastructure.

Python · FastAPI · PostgreSQL · Redis · Docker · Next.js — 73 tests, ~93% line coverage, 5 CI jobs — source

Problem

Customer webhook endpoints are flaky: timeouts, 5xx responses, deploys mid-delivery. Sending the POST inside the producer's request handler couples API latency to the customer's worst day — and a failed POST means a lost event.

Constraints

  • One primary service, one database, one queue. No Kafka, no Kubernetes.
  • Redis is optional: the system must stay correct with plain database polling.
  • Receivers must be able to verify every delivery and safely retry it.

Architecture

Client
  ↓ POST /v1/events (API key, validate, Idempotency-Key)
FastAPI (tenants, endpoints, ingest, history)
  ↓ persist first
PostgreSQL (tenants, endpoints, events, deliveries — Alembic migrations)
  ↓ notify (wake-up hint)
Redis list ──→ Workers (atomic claim + lease, FOR UPDATE SKIP LOCKED)
  ↓ sign + POST + timeout
Customer webhook (verifies X-Hookflow-Signature)
  ↓
Delivery history + DLQ replay + /metrics + /v1/stats + operator dashboard

Implementation

Ingest validates (http(s) URL, JSON-serializable payload under 256KB), checks idempotency, then commits Event + Delivery(status=queued) in a single transaction before touching Redis — schema managed by Alembic migrations with a CI gate that fails on model/migration drift. The worker signs each POST with per-endpoint HMAC-SHA256 (X-Hookflow-Signature: sha256=…), enforces a 10s timeout, and settles the row: success, retrying with backoff, or dead-letter after 5 attempts (1m → 5m → 30m → 2h → 12h). Webhook secrets are encrypted at rest (Fernet envelope); tenants are isolated with per-tenant API keys (SHA-256 digest stored, plaintext shown once). A replay endpoint resets dead-letter rows to queued; successes are not requeueable, since replaying one would duplicate a side effect at the receiver. Per-endpoint fixed-window rate limits, request IDs on every response, and Prometheus-text /metrics plus /v1/stats (queue depth by status) cover observability. A Next.js operator dashboard sits on top: overview, endpoints, deliveries, DLQ with replay, metrics, and key management.

Engineering decisions

  • Persist before enqueue. An accepted event is never lost even if Redis drops the wake-up, because the worker polls due rows.
  • At-least-once + idempotency keys instead of exactly-once claims. A UNIQUE(endpoint_id, idempotency_key) constraint plus an IntegrityError catch closes the race where two concurrent ingests both pass the app-level existence check — the loser returns the winner as deduplicated.
  • Atomic multi-worker claims with leases. Workers claim due rows in one transaction (FOR UPDATE SKIP LOCKED, claim token, 60s lease) so N workers never queue behind each other and a crashed worker's rows become claimable again instead of stuck. See Concurrency below.
  • Worker poll indexed on (status, next_attempt_at) so the 2s poll never full-scans.
  • Observability without new dependencies — in-process counters, request-ID middleware, stats endpoint.

Concurrency

Two workers can observe the same pending delivery. The fix is a claim issued as a single UPDATE whose subquery excludes rows already claimed under a live lease — the database serialises the two racers, and the loser's subquery is re-evaluated against the winner's committed rows, so it simply finds fewer candidates. A plain SELECT-then-UPDATE would not be safe. On PostgreSQL the subquery additionally uses FOR UPDATE SKIP LOCKED so N workers never queue behind each other; each claim carries a token plus a 60s lease, so a crashed worker's rows become claimable again instead of stuck. A worker settles each row only while it holds the token; success releases the claim and a sweeper frees stale ones. The test suite drives real overlapping claimers and asserts disjoint claim sets — zero double delivery — plus lease expiry, claim release on settle, and rate-limited deliveries never stranded.

Challenges

The idempotency race above was the sharpest edge: the app-level "does this key exist?" check is correct for sequential requests and wrong under concurrency. The UNIQUE constraint is the actual guarantee; the application code is the friendly path. Testing it meant driving two overlapping ingests rather than trusting the single-threaded test.

Trade-offs

  • Memory rate-limit/queue fallback is single-replica only — documented, not hidden. The claim path is replica-safe; the limiter is not.
  • Secrets are encrypted, not hashed, because the server must reproduce them to sign — documented in docs/security.md, with unknown envelope versions rejected loudly.
  • API keys have no expiry and there are no per-tenant quotas yet; revocation exists, rotation does not.
  • Backoff schedule is fixed at config level, not per endpoint. No TLS in Compose; terminate at a load balancer.

Operator dashboard

A Next.js dashboard over the same API: overview queue depth, endpoints management, deliveries history, DLQ with one-click replay, metrics, and API key management. The interface is the product surface; the claim/lease mechanism is the engineering underneath.

Lessons

Webhook delivery is a persistence problem, not a POST problem. The interesting work is all in the failure paths: what happens when the receiver is down, when Redis is down, when two producers race. Each got a mechanism (polling fallback, backoff + DLQ, UNIQUE constraint) plus a test.
