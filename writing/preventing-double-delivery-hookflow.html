Preventing double delivery under concurrent workers

Two workers can observe the same pending delivery. The claim has to be atomic.

HookFlow's first version had one worker, so delivery correctness was trivially true: poll due rows, POST, settle. The moment a second worker exists, "poll due rows" becomes a race — both workers can read the same free row before either writes. I fixed it with a claim instead of a lock held across the HTTP call.

The mechanism

claim_due_deliveries takes ownership in a single UPDATE whose subquery excludes rows already claimed under a live lease. The database serialises the two racers, and the loser's subquery is re-evaluated against the winner's committed rows — it simply finds fewer candidates. A plain SELECT-then-UPDATE would not be safe. On PostgreSQL the subquery additionally uses FOR UPDATE SKIP LOCKED so N workers never queue behind each other (SQLite has no row locks but serialises writers anyway). Each claim carries a token plus a 60-second lease:

  • A worker settles a row only while it holds the token; success releases the claim.
  • A crashed worker's rows become claimable again once the lease expires — stuck rows are impossible by construction, and a sweeper frees stale claims explicitly.
  • Rate-limited deliveries are settled back without a claim so they are never stranded.

The test that matters

test_concurrent_claimers_receive_disjoint_rows drives real overlapping claimers and asserts disjoint claim sets — zero double delivery. Around it: lease expiry makes rows claimable again, settling releases the claim, the sweeper frees only stale rows, and unclaimed mode still selects everything for the single-worker case where claiming would be pure overhead.

What I kept honest

The delivery claim is safe across replicas; the rate limiter is not when Redis is off — per-process fallback is single-replica only, stated in the README limitations. The claim tests run against SQLite; the SKIP LOCKED path is PostgreSQL-only by dialect check. I cite the mechanism and the tests, not a Postgres concurrency benchmark I haven't run.
